Purpose

Pure Storage Host Validation / Readiness is a read-only Windows host audit tool for Pure Storage FlashArray environments. It validates Windows, networking, iSCSI, MPIO, Hyper-V, Failover Cluster, Pure target connectivity, and optional Pure ActiveCluster host-side readiness.

Operating principle: this tool answers, “Is this Windows host correctly prepared and connected for Pure Storage?” Configuration and remediation belong in the iSCSI Host Tool or an approved manual change workflow.

The validator does not configure hosts, create iSCSI sessions, initialize disks, create volumes, map LUNs, create CSVs, or modify FlashArray configuration.

Prerequisites

  1. Run from Windows PowerShell 5.1 as an elevated administrator.
  2. WinRM / PowerShell remoting must be available to remote target hosts.
  3. The supplied Windows credential must have administrative rights on the target hosts.
  4. For Pure target-connectivity tests, enter the Pure iSCSI target IP addresses.
  5. For Hyper-V or Failover Cluster validation, enable the applicable audit scope.
  6. For ActiveCluster validation, assign Pure targets to arrays and hosts to their local arrays in the GUI.

Recommended Workflow

  1. Enter the target Windows hosts.
  2. Enter all intended Pure iSCSI target IP addresses.
  3. Confirm the iSCSI NIC naming pattern and expected storage MTU.
  4. Select the required audit scopes.
  5. If ActiveCluster is used, configure topology, array names, target-to-array assignment, host-local-array mapping, MPIO policy, and minimum target paths.
  6. Set the Windows credential or select Use Current User.
  7. Run Read-Only Audit.
  8. Review FAIL and WARNING results first.
  9. Review Host Drift Summary and MPIO Summary.
  10. Export the HTML report.
  11. Perform approved remediation outside this validator.
  12. Re-run the audit to verify the resulting state.

Main Configuration Fields

Target Hosts

Enter one Windows host per line. The field starts blank intentionally so the administrative workstation is not automatically audited.

host01
host02
host03

Pure iSCSI Target IPs

Enter every Pure iSCSI target IP that should be reachable from the audited hosts, one per line. The validator tests TCP/3260 and records the Windows interface and source address selected for the route.

iSCSI NIC Name Pattern

Default: iSCSI*. This pattern identifies dedicated Windows storage NICs.

Expected Storage MTU

Default: 9000. The validator compares the intended storage MTU to the Windows IP-interface MTU and the NIC driver Jumbo Packet setting.

MTU/Jumbo remediation is never automatic. End-to-end switch, VLAN, host, and Pure target support must be verified first.

Array Names

Array A and Array B names are friendly report labels. They do not establish a FlashArray connection and do not modify array configuration.

Target-to-Array Assignment

The list is populated from the configured Pure iSCSI target IPs. Every target must be assigned to Array A or Array B before ActiveCluster validation can run.

Host Local-Array Mapping

The list is populated from Target Hosts. Each host is assigned the Pure array expected to be local/preferred for host-side topology validation. This does not modify the FlashArray preferred-array setting.

Pure MPIO Policy Validation

Pure Recommended (Auto) evaluates Pure Storage policy according to actual per-device path count when that runtime data is available.

Observed Paths per Pure DevicePolicy Evaluation
1-10RR or LQD is valid. RR is identified as preferred.
11-32LQD is expected.
More than 32Hard FAIL for the Windows path-limit rule. Reduce presented paths.
Not yet availableHost/default policy is evaluated provisionally. Per-device policy becomes authoritative after Pure volumes are presented.

The validator keeps two concepts separate:

  • Host/global MSDSM policy readiness: what newly discovered Pure devices are likely to inherit.
  • Per-device MPIO policy: the actual policy of each visible Pure device. This becomes authoritative once storage is connected.

A newly added path belongs to the existing MPIO device. Individual paths do not have their own load-balancing policy. If path expansion crosses the 10-path threshold, the validator re-evaluates the device policy.

Windows MPIO Path Limit

Windows supports a maximum of 32 MPIO paths per device.

Path CountResultMeaning
1-32PASSWithin the Windows supported maximum.
>32FAILExceeds the supported Windows MPIO path count.
Not correlatedINFOThe validator cannot safely determine an authoritative per-device path count and does not guess.

The MPIO Summary reports the maximum observed path count for any correlated Pure device on each host and shows the Windows maximum beside it.

ALUA Validation

When Pure disks are visible, the tool attempts read-only Microsoft DSM ALUA inspection through Windows WMI/CIM data.

Recognized states include:

  • Active/Optimized
  • Active/Unoptimized
  • Standby
  • Unavailable
  • Not Used

Uniform and Non-Uniform topology modes have different expected ALUA behavior. If the validator cannot safely correlate MSDSM/ALUA data with a Pure device, it reports INFO instead of inferring ownership.

Result Severity

SeverityMeaning
PASSThe observed state meets the validation rule.
INFOInformational state, build-stage observation, or a condition not yet authoritatively testable.
WARNINGThe state differs from the recommended or expected configuration but is not a hard failure.
FAILThe state violates a required rule or supported limit.

HTML Report

Use Export HTML Report after an audit. The exported report contains:

  • Audit metadata and tool version
  • Overall status
  • PASS / INFO / WARNING / FAIL totals
  • Host Drift Summary
  • MPIO Summary
  • Detailed Results grouped by severity and host
  • Remediation Items with recommended action, risk, verification, and rollback guidance

View HTML Report opens the most recently exported report from the current application session.

Expected Pre-Connection State

Before Pure volumes are presented, several INFO results are normal and do not represent failures.
  • 0 configured target portals
  • 0 active iSCSI sessions
  • 0 Pure disks
  • 0 cluster physical disks
  • 0 CSVs
  • ALUA validation = INFO
  • MPIO Max Paths / Device = Not available

Post-Storage Connection Validation

After Pure volumes and iSCSI sessions exist, run the full audit again. The following checks then become authoritative:

  • Runtime Pure iSCSI session and connection state
  • Source-NIC/source-IP path symmetry
  • Unexpected live target addresses
  • Per-Pure-device MPIO policy
  • Per-device Windows path-count limit
  • ALUA path states
  • ActiveCluster runtime topology

Remediation Safety

This validator is read-only. Remediation commands shown in the report are advisory and are never executed by this tool.
  • Microsoft network bindings may later be suitable for confirmed remediation in the configuration tool.
  • Persistent default routes can be handled through an approved remediation workflow.
  • MTU/Jumbo changes remain guided-only.
  • ActiveCluster topology/pathing and ALUA corrections remain guided-only.
  • MPIO policy changes belong in the configuration tool and require explicit confirmation.

Out of Scope

The validator does not:

  • Create or delete Pure hosts
  • Create or modify Pure host groups
  • Create Pods or Protection Groups
  • Create volumes or assign LUNs
  • Connect volumes to hosts or host groups
  • Configure iSCSI target portals or sessions
  • Initialize or format disks
  • Create Failover Clusters or CSVs
  • Change MPIO policy
  • Change MTU or Jumbo Packet settings
  • Modify FlashArray preferred-array settings

Troubleshooting

No host results

Verify host names, credentials, WinRM, firewall policy, and administrator rights.

Pure target TCP test fails

Verify target IP, VLAN/routing, switch configuration, source NIC selection, Pure iSCSI interface state, and TCP/3260 reachability.

MPIO path count shows “Not available”

This is expected before Pure disks are presented. If Pure disks are already visible, inspect Detailed Results for MSDSM/ALUA correlation information.

ALUA remains INFO after storage is presented

Inspect the Detailed Results. The validator intentionally refuses to infer ALUA ownership when the Windows data cannot be safely correlated.

HTML audit report cannot be opened

Export the report first and verify that the selected destination remains accessible.
